# 2026-09-12 · Mobile chat responsiveness and readable replies

In the mobile chat, the composer could sit behind navigation, Markdown appeared as plain text, and sending stayed locked while optional run details loaded after an answer. This update keeps the composer above navigation and the on-screen keyboard, renders readable paragraphs and lists, and unlocks the next question as soon as the reply arrives.

Slow history loading no longer blocks a new question. Late history and run details cannot overwrite newer interaction state. Early questions on a report page retain their answer or retry state rather than being immediately folded into an automatic report. Drafts stay local to the composer, and historical messages render on demand.

The backend implementation in this commit explicitly disables thinking for interactive calls to the official DeepSeek API and uses a bounded answer budget with concise mobile formatting. Truncated or empty answers fail explicitly; deterministic report fallback remains labeled. Background planning and weekly-report calls are unchanged. Permissions, safety checks, and audit behavior remain in place. **These backend changes are not included in the public deployment described below.**

## Public deployment

[Open the updated PoopSense mobile demo](https://poopsense-mobile.vercel.app/). The public frontend was verified on 2026-09-12; its JavaScript and CSS match the local production build. It uses a same-origin proxy to the existing `poopsense-live-demo.vercel.app` backend. This deployment delivers the frontend interaction and readability changes; the new backend model settings remain undeployed.

At 23:29 Beijing time, one real ordinary chat request succeeded: the reply appeared and sending unlocked after **13.771 seconds**; optional run details completed after **14.184 seconds** without continuing to block the composer. The response reported `model_version=deepseek-v4-pro` and `report=null`. The browser rendered three list items and three bold spans.

The earlier baseline request took **11.335 seconds**. These individual requests do **not** show a model-speed improvement. A separate direct check of the new local backend function completed in **12.878 seconds**, returning 221 characters in three paragraphs with `finish_reason=stop`; it verifies parameter support for that call, not a deployed latency improvement or a response-time guarantee.

The demo still uses shared fictional data and temporary storage. It does not establish durable history, long-term production availability, real WeChat keyboard behavior, or performance under all mobile network conditions.
